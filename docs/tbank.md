# Т-Банк

Проект работает с API Т-Банка (`https://securepay.tinkoff.ru/v2`): `Init`,
`Charge`, `GetState`, `Cancel`. Оплата — в копейках, ключи терминала — только
в `.env`.

## Терминалы

Нужны два терминала:

- **тестовый** — для проверки сценариев без реальных денег;
- **боевой** — для приёма платежей.

Для каждого заполняются `TBANK_TERMINAL_KEY` и `TBANK_PASSWORD`. Не
используйте боевые ключи в тестах и не коммитьте их.

## Подпись

Токен запроса — SHA-256 от конкатенации значений корневых полей, отсортированных
по имени ключа, плюс пароль терминала:

```text
sha256(concat(sorted(key + value)) + Password)
```

Правила:

- `Token` и `Password` в подпись не входят;
- вложенные объекты и массивы (`Receipt`, `DATA`) не входят;
- булевы значения приводятся к `true` / `false`;
- `null` и пустая строка дают пустую строку;
- сравнение подписи — в постоянном времени.

Пример:

```python
from app import tbank

payload = {
    "TerminalKey": "<terminal_key>",
    "Amount": "<amount_kopecks>",
    "OrderId": "<order_id>",
    "Description": "<описание>",
}
payload["Token"] = tbank.make_token(payload, "<password>")
```

## Init

`Init` создаёт платёж и возвращает `PaymentId` и `PaymentURL`.

```json
{
  "TerminalKey": "<terminal_key>",
  "Amount": "<amount_kopecks>",
  "OrderId": "<уникальный order_id>",
  "Description": "<описание без двойных кавычек>",
  "CustomerKey": "<tg_id клиента>",
  "Recurrent": "Y",
  "Receipt": {
    "Taxation": "usn_income",
    "Items": [
      {
        "Name": "<название тарифа>",
        "Price": "<цена в копейках>",
        "Quantity": 1,
        "Amount": "<цена в копейках>",
        "Tax": "none"
      }
    ],
    "Email": "<email>"
  },
  "NotificationURL": "https://<ваш-домен>/tbank/notify"
}
```

В реальном запросе суммы — числа, здесь показаны placeholder-строки для
наглядности.

`OrderId` уникален; в проекте он строится как `<tg_id>-<случайный суффикс>`.
`CustomerKey` — Telegram ID клиента. `Recurrent: "Y"` разрешает сохранить
карту для будущих списаний.

## Рекуррентные списания

1. Первый платёж проходит через `Init` и оплату на стороне банка.
2. В уведомлении приходит `RebillId`; он сохраняется в подписке.
3. Следующее списание: `Init` с `Recurrent: "N"` и
   `OperationInitiatorType: "R"`, затем `Charge` с `PaymentId` и `RebillId`.
4. При успехе период продлевается, при отказе включается дуннинг.

Замена карты — отдельный платёж на минимальную сумму: после подтверждения
новый `RebillId` заменяет старый, доступ не продлевается.

## Чеки

Чек формируется по 54-ФЗ:

- `Taxation`: `usn_income`;
- одна позиция — тариф;
- `Price` и `Amount` — в копейках;
- `Quantity`: 1;
- `Tax`: `none`;
- `Email` или `Phone` — что есть у клиента.

В корне `Receipt` не должно быть поля `Amount`: сумма передаётся в корне
запроса `Init`. Если у клиента нет email и телефона, чек собрать нельзя —
такой платёж нужно остановить и запросить контакты.

## Уведомления

Банк присылает POST на `/tbank/notify`.

Порядок обработки:

1. Проверить подпись.
2. Всегда сохранить событие в `payment_events` — даже с плохой подписью.
3. Найти платёж по `PaymentId`, затем по `OrderId`.
4. Сверить сумму с `payments.amount_kopecks`.
5. Обработать статус.

Статусы:

- `CONFIRMED` — активировать или продлить подписку;
- `REJECTED`, `CANCELED`, `CANCELLED` — отметить платёж отклонённым;
- остальные — сохранить событие и ничего не менять.

Повторное уведомление по уже подтверждённому платежу не продлевает подписку
второй раз. При неверной подписи возвращается `403`, событие всё равно
остаётся в базе для разбора.

## Ошибки

| Ситуация | Поведение |
| --- | --- |
| Сетевой сбой, таймаут, 5xx | `RetryLater`, задача `reconcile` через 15 минут; попытки не увеличиваются. |
| Бизнес-отказ банка | Платёж `rejected`, увеличивается `failed_attempts`, включается дуннинг. |
| Нет `PaymentId` в ответе | Платёж отклоняется с кодом `invalid_response`. |
| Нет `RebillId` при продлении | Платёж отклоняется с кодом `no_rebill`. |
| Сумма в уведомлении не совпала | Событие сохраняется, подписка не меняется, ошибка в лог. |
| Неизвестный платёж | Событие сохраняется, банку возвращается `OK`. |
| Неверная подпись | `403`, событие сохраняется с `signature_ok=false`. |

Ошибки банка сохраняются в `payments.error_code` и
`payments.error_message`. Логи не должны содержать пароль и полный токен.

## Тестовый терминал

1. Создайте тестовый терминал и заполните тестовые ключи.
2. Проведите `Init` → оплату тестовой картой → уведомление → активацию.
3. Проверьте повторное уведомление: подписка не должна продлиться дважды.
4. Проверьте отказ карты и повторные попытки.
5. Проверьте замену карты.

Перед боевым запуском сделайте живой тест 1 ₽:

- только с письменным согласием клиента;
- сумма 100 копеек, сразу возврат через `Cancel`;
- нужны `RebillId`, email или телефон для чека;
- после теста проверьте, что подписка клиента не продлилась, а возврат
  виден в кабинете.

Подробный чек-лист переключения — в
[salebot-migration.md](salebot-migration.md).

## Безопасность

- HTTPS обязателен: уведомления идут на публичный URL.
- Подпись проверяется до любых изменений.
- Сумма сверяется с сохранённым платежом.
- Ключи терминала не попадают в логи, тесты и git.
- При подозрении на утечку: остановить `billing`, сменить ключи, проверить
  `payments` и `payment_events`, при необходимости вернуть деньги вручную.
