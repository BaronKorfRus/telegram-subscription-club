# Архитектура

## Компоненты

| Процесс | Роль |
| --- | --- |
| `web` | FastAPI: `/healthz` и приём HTTP-уведомлений Т-Банка `/tbank/notify`. |
| `bot` | aiogram, long polling: регистрация, меню, статус подписки, оплата, ответы админов. |
| `billing` | Фоновый воркер: напоминания, списания, удаление доступа, отчёты, сверка. |
| `heartbeat` | Проверяет локальный `/healthz` и отправляет сигнал внешнему сторожу. |
| `db` | PostgreSQL: клиенты, тарифы, подписки, платежи, события, задачи, сообщения. |
| `tgproxy` | Необязательный SOCKS5-прокси для доступа к Telegram API. |

Все процессы собираются из одного Docker-образа и запускаются с разными
командами. Общая база — единственная точка согласования состояния.

## Сети

В `docker-compose.yml` три сети:

- `internal` — внутренняя, без выхода наружу; в ней живут приложение и база.
- `egress` — исходящий интернет для `bot` и `billing`.
- `edge` — внешняя общая сеть с Caddy; `web` доступен в ней как `club-web:8000`.

Caddy терминирует TLS и проксирует запросы на `web`. База и воркеры не
публикуются наружу.

## Данные

| Таблица | Назначение |
| --- | --- |
| `clients` | Клиент Telegram: `tg_id`, имя, username, телефон, email. |
| `tariffs` | Тариф: код, название, цена в копейках, срок, флаги legacy/active. |
| `subscriptions` | Подписка: тариф, статус, конец периода, автопродление, `rebill_id`, маска карты, число неудач. |
| `payments` | Платёж: вид, сумма, `order_id`, `bank_payment_id`, статус, чек, ошибка. |
| `payment_events` | Сырые события банка и результат проверки подписи. |
| `jobs` | Очередь задач: тип, время запуска, payload, статус, попытки, блокировка. |
| `messages` | История сообщений клиента, бота, админа и сервисных. |
| `admin_message_links` | Связь пересланного админу сообщения с клиентом. |
| `admins` | Админы и владелец, статус заявки. |
| `notification_errors` | Ошибки доставки сообщений в Telegram. |

Даты периодов хранятся как календарные даты, время задач — с часовым поясом
из `TZ` (по умолчанию `Europe/Moscow`).

## Окно оплаты и месячные периоды

`app/services/window.py` — единственный источник правды про окно. Дни окна
берутся из `PAYMENT_WINDOW_START_DAY` / `PAYMENT_WINDOW_END_DAY` (по
умолчанию 22–24), а модуль отвечает на три вопроса: открыто ли окно сейчас,
когда следующее и как его назвать в тексте.

- Гейт стоит в `payments.create_payment`: вне окна создание платежа падает с
  `WindowClosedError`, кроме замены карты (`card_change`).
- Регистрация вне окна проходит, но вместо тарифов бот показывает текст с
  датой следующего окна.
- Длительность периода — `tariffs.period_months`; конец периода считается
  функцией `subscriptions.add_months` от текущего окончания (или от
  `forced_period_end`, если он задан), поэтому дата всегда падает на
  `PAYMENT_WINDOW_START_DAY`.
- Истечение не привязано к третьей неудаче списания: `schedule_cycle` ставит
  задачу `expire_check` на `конец периода + 3 дня` в 00:05 (то есть 25-го).
  Задача срабатывает, только если период так и не продлили, поэтому оплата
  23–24-го спасает доступ.
- Напоминания тем, у кого нет доступа, ставит `window_notices.maybe_schedule`
  на `START_DAY - 3` и на `START_DAY` в 12:00; идемпотентность — по дате в
  `payload`.

`scripts/align_periods.py` разово приводит существующие даты к якорному дню и
пересобирает задачи цикла; по умолчанию он работает в режиме dry-run.

## Первичная оплата

1. Бот создаёт строку `payments` со статусом `created` и уникальным
   `order_id`.
2. Вызывается `Init` Т-Банка. В ответ приходят `PaymentId` и `PaymentURL`.
3. Платёж переходит в `pending`, клиент открывает ссылку и платит.
4. Банк присылает HTTP-уведомление на `/tbank/notify`.
5. `web` проверяет подпись, сохраняет `payment_events`, находит платёж по
   `PaymentId` или `OrderId` и сверяет сумму.
6. При `CONFIRMED` создаётся или продлевается подписка, ставится цикл
   напоминаний и задача `post_payment`.
7. `post_payment` выдаёт доступ в канал и чат и отправляет ссылку.

Если `Init` не удался, платёж остаётся в базе со статусом `rejected` — это
удобно для разбора, а не «платёж-призрак».

## Продление и дуннинг

Списание возможно только внутри окна оплаты. Если задача `charge` созрела вне
окна (например, после ручного вмешательства), деньги не списываются: задача
переносится на ближайший якорный день в 09:00.

- Успех: период продлевается, счётчик неудач сбрасывается, планируется
  следующий цикл.
- Отказ карты: платёж `rejected`, подписка `past_due`, повтор на следующий
  день в 09:00.
- Второй отказ: повтор ещё раз на следующий день в 09:00.
- Третий отказ: подписка остаётся `past_due`, клиент получает сообщение о том,
  что доступ сохраняется до конца окна. Истечение и удаление доступа делает
  отдельная задача `expire_check` 25-го.
- Сетевой сбой или 5xx: это не отказ карты. Попытки не увеличиваются,
  создаётся задача `reconcile` через 15 минут, состояние уточняется через
  `GetState`.

Если банк не дал однозначного ответа, новая `Init` не создаётся: сначала
проверяется уже созданный платёж. Это защищает от двойных списаний.

## Планировщик

Задачи лежат в таблице `jobs`; отдельного брокера нет.

- Воркер забирает готовые задачи через `SELECT ... FOR UPDATE SKIP LOCKED`.
- Задача блокируется на 5 минут; если воркер упал, блокировка истекает и
  задачу может взять другой процесс.
- При ошибке задача возвращается в очередь с backoff (1, 5, 15, 60 минут).
- После 5 попыток задача переходит в `failed` и попадает в лог.
- `schedule_cycle` заменяет старые pending-задачи того же типа для этой
  подписки, поэтому повторный вызов не создаёт дублей.

Типы задач: `reminder_3d`, `reminder_1d`, `charge`, `expire`, `expire_check`,
`kick`, `reconcile`, `post_payment`, `payment_failed`, `daily_report`,
`window_soon`, `window_open`.

Воркер каждый цикл также вызывает `window_notices.maybe_schedule`, чтобы
напоминания о окне существовали, даже если подписка не менялась.

## Идемпотентность

- `payments.order_id` и `payments.bank_payment_id` уникальны.
- Повторное уведомление с тем же `PaymentId` не продлевает подписку второй
  раз: проверяется текущий статус платежа.
- `payment_events` сохраняется всегда, даже при плохой подписи.
- `post_payment_done` не даёт выдать доступ и отправить ссылку повторно.
- `schedule_cycle` удаляет старые pending-задачи перед постановкой новых.
- Миграция из Salebot делает upsert по `tg_id`, поэтому её можно запускать
  повторно.

## Доступ

- После оплаты `unbanChatMember` снимает бан в канале и чате, чтобы клиент
  мог войти по ссылке.
- При отмене или истечении `banChatMember` удаляет доступ.
- Заявка на вступление в канал одобряется через `approveChatJoinRequest`.
- Если Telegram недоступен, задача `kick` повторяется каждые 5 минут в
  течение 24 часов.
- Ссылка на канал и ID канала/чата задаются только в `.env`.

## Отчёты и мониторинг

- `daily_report` собирает сводку по списаниям, отказам, повторным попыткам и
  ошибкам доставки. Ближайшие плановые даты сводка берёт из базы
  (`reports.upcoming_dates`), а не из констант; если действующих подписок нет,
  блок не печатается.
- `/healthz` проверяет доступность базы.
- `heartbeat` раз в минуту отправляет POST внешнему сторожу; если локальный
  `/healthz` не 200, сигнал не отправляется — для сторожа это тревога.
- Все ошибки доставки сообщений сохраняются в `notification_errors`.

## Границы

Проект рассчитан на один клуб и один платёжный терминал. Мультитенантность,
веб-кабинет и другие платёжные провайдеры в текущую архитектуру не входят.
