# Безопасность

Документ описывает модель угроз, работу с секретами и персональными данными,
а также порядок действий при инциденте. Как сообщить об уязвимости —
[SECURITY.md](../SECURITY.md).

## Что защищаем

- **Секреты:** токен бота, пароль терминала Т-Банка, ключ Salebot, пароль
  PostgreSQL, токен хартбита, SSH-ключи.
- **Персональные данные клиентов:** Telegram ID, имя, username, телефон,
  email, маска карты.
- **Деньги:** рекуррентные списания и возвраты.
- **Доступ в клуб:** канал и чат.

## Модель угроз

| Угроза | Последствие | Защита |
| --- | --- | --- |
| Утечка `.env` | Чужой доступ к боту и платежам | `.env` вне git, права `600`, ротация ключей |
| Поддельное уведомление банка | Ложное продление подписки | Проверка подписи и суммы |
| Повтор уведомления | Двойное продление | Идемпотентность по `PaymentId` и статусу |
| Кража `rebill_id` | Списание чужих денег | `rebill_id` только в базе, доступ к базе ограничен |
| Слабый пароль БД | Утечка персональных данных | База не публикуется наружу, сложный пароль |
| Компрометация сервера | Всё сразу | Обновления, SSH по ключам, минимум сервисов |
| Ошибочная выдача доступа | Бесплатный вход в клуб | Доступ только по действующей подписке |
| Логи с секретами | Утечка через логи | Токены не попадают в текст ошибок |

Проект не претендует на защиту от скомпрометированного сервера или
злоумышленника с root-доступом. Это базовая, но не абсолютная защита.

## Секреты

- Все секреты — в `.env`; файл исключён из git.
- Права на файл: `chmod 600 .env`.
- Отдельные ключи для тестового и боевого терминалов.
- Ключ Salebot нужен только на время миграции; после переезда его лучше
  отозвать.
- Не передавайте секреты в чатах, issue и pull request. Если секрет попал в
  переписку или лог — считайте его скомпрометированным и перевыпустите.
- Не печатайте `.env` целиком. Для проверки используйте маскирование:

```bash
sed -E 's/(TOKEN|PASSWORD|KEY)=.*/\1=<hidden>/' .env
```

- Токен бота не выводится в ошибках: клиент Telegram API не прикладывает URL
  запроса к исключению.
- Пароль терминала не попадает в подпись и в логи.

## Подпись уведомлений Т-Банка

Уведомление считается доверенным только после проверки `Token`.

- Подпись — SHA-256 от значений корневых полей, отсортированных по имени
  ключа, плюс пароль терминала.
- `Token` и `Password` в подпись не входят; вложенные объекты не входят.
- Сравнение — в постоянном времени (`hmac.compare_digest`).
- Событие сохраняется в `payment_events` в любом случае, даже при неверной
  подписи, — это нужно для разбора.
- При неверной подписи возвращается `403`, и никакие данные подписки не
  меняются.
- Сумма из уведомления сверяется с сохранённым платежом. Расхождение — повод
  для ручного разбора, а не для продления.

Дополнительно:

- HTTPS обязателен: уведомления идут на публичный URL.
- Публичный URL не должен быть предсказуемым секретом; защита — в подписи.
- Ограничьте доступ к кабинету терминала и включите уведомления только на
  свой домен.

## Доступ в клуб

- Бот должен быть администратором канала и чата.
- Выдача доступа — только после подтверждённого платежа.
- Удаление — при отмене, истечении или исчерпании попыток.
- Заявка на вступление одобряется только при действующей подписке; остальные
  отклоняются.
- Ссылка-приглашение и ID канала/чата — в `.env`, не в коде и не в
  публичной документации.
- Админы бота подтверждаются владельцем вручную. Права администратора не
  выдаются автоматически.
- Владелец — единственный, кто подтверждает и отклоняет заявки админов.

## Персональные данные

Проект хранит минимально необходимые данные:

- Telegram ID, имя, username;
- телефон и email — для чеков и связи;
- маску карты и `rebill_id` — для продлений;
- историю сообщений и платежей.

Правила:

- Собирайте только то, что нужно для оплаты и доступа.
- Перед переносом данных из Salebot или другого сервиса получите согласие
  клиентов и проверьте требования законодательства о персональных данных.
- Не публикуйте выгрузки, `.sbk`-схемы и списки клиентов.
- Ограничьте доступ к базе и бэкапам.
- Бэкапы шифруйте или храните на защищённом хосте.
- Удаляйте данные по запросу клиента, если это не противоречит требованиям
  к бухгалтерским документам.
- Для тестов используйте вымышленные данные, а не копию боевой базы.

## Логи

- Логи не должны содержать токены, пароли, полные номера карт и содержимое
  `.env`.
- Клиент Telegram API намеренно не прикладывает причину сетевой ошибки: в URL
  находится токен бота.
- HTTP-клиент Salebot логируется на уровне `WARNING`, потому что ключ
  передаётся в path.
- Ошибки доставки сообщений сохраняются в `notification_errors`; это
  внутренние данные, не публикуйте их.
- При разборе инцидента логи полезны, но их тоже нужно считать чувствительными.

## База данных

- PostgreSQL не публикует порт наружу; доступ только из внутренней сети.
- Пароль базы — сложный и уникальный, не `club` из примера.
- Пользователь приложения не должен иметь прав суперпользователя.
- Миграции применяются отдельной командой, а не автоматически при старте.
- Перед обновлением схемы — бэкап.
- Доступ к `psql` — только у администратора сервера.

## Сервер

- SSH по ключам, вход по паролю и root-логин отключены.
- Только необходимые порты: `80` и `443` для Caddy.
- Обновления ОС, Docker-образа и зависимостей — регулярно.
- Отдельный пользователь для деплоя, минимум прав.
- Внешний сторож живёт вне сервера: падение сервера не должно отключать
  тревогу.
- Бэкапы хранятся вне сервера.
- Секреты не попадают в историю shell и в аргументы командной строки.

## Миграция и переключение

- Перед переездом — бэкап и проверенная точка восстановления.
- Ключи Т-Банка убираются из старой системы до запуска нового биллинга, иначе
  возможны двойные списания.
- Старый `NotificationURL` и вебхук сохраняются для отката.
- Живой тест 1 ₽ — только с письменным согласием клиента.
- После переключения проверьте `payment_events`, `payments` и отсутствие
  дублей.

## Инцидент

1. Остановите `billing`, чтобы исключить новые списания.
2. Смените скомпрометированные ключи: токен бота, пароль терминала, пароль
   базы, ключ Salebot.
3. Проверьте `payments` и `payment_events` за период инцидента.
4. Сверьте списания в кабинете банка; при необходимости верните деньги
   вручную.
5. Проверьте доступ в канал и чат: нет ли лишних участников.
6. Сохраните логи и события до очистки.
7. Восстановите сервис с новыми ключами и проверьте тестовым платежом.
8. Разберите причину и закройте её, а не только симптом.

## Ограничения

- Нет ролевой модели кроме «владелец / админ / клиент».
- Нет отдельного аудита действий администраторов, кроме истории сообщений.
- Нет автоматического шифрования базы на уровне приложения.
- Нет встроенной защиты от DDoS: этим занимается Caddy и провайдер.
- Соответствие требованиям к персональным данным — ответственность владельца
  клуба, а не гарантия кода.
