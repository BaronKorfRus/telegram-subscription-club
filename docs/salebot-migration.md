# Переезд с Salebot Pro

**Salebot Pro** (`https://salebot.pro`) — конструктор ботов без кода. Сценарий
собирается из блоков, данные клиентов хранятся в переменных, платежи
подключаются через интеграции. Платформа закрытая и большая: кроме ботов в ней
есть рассылки, CRM и аналитика.

Этот документ — для тех, у кого в Salebot Pro собран простой бот: приветствие,
выбор тарифа, оплата, доступ и продление. Если вы используете малую часть
платформы, свой сервис даёт то, чего конструктор не даёт: код и данные у вас,
логику видно целиком, платежи идут напрямую в Т-Банк, а стоимость не зависит
от числа клиентов в конструкторе.

Если клуб раньше жил в Salebot Pro, перенести клиентов и логику можно тремя
путями. Они не исключают друг друга: API даёт данные, `.sbk` помогает понять
сценарий, а код этого проекта показывает, как те же шаги устроены после
переезда.

Перед переносом персональных данных получите согласие клиентов и проверьте
требования законодательства о персональных данных.

## Путь 1. API Salebot Pro

### Выгрузка клиентов

Нужны `SALEBOT_API_KEY` и `SALEBOT_API_BASE` в `.env`. Ключ даёт доступ к
данным, поэтому храните его только в `.env`.

Запросы:

```bash
# список клиентов
curl -sS "https://<salebot-api>/<api_key>/get_clients?limit=500"

# переменные одного клиента
curl -sS "https://<salebot-api>/<api_key>/get_variables?client_id=<client_id>"
```

Ответ `get_clients` — список клиентов. У каждого есть `id` (внутренний ID
Salebot Pro) и `platform_id` (Telegram ID). Переменные могут лежать как в корне
клиента, так и в `variables` / `vars`; `get_variables` возвращает их
отдельно.

Пример ответа (сокращённо):

```json
{
  "result": [
    {
      "id": "<client_id>",
      "platform_id": "<tg_id>",
      "name": "<имя>",
      "variables": {
        "tarif": "<код тарифа>",
        "datespis": "<дата окончания>",
        "phone": "<телефон>",
        "email": "<email>",
        "tinkoff_rebill_id": "<rebill_id>",
        "card_mask": "<маска карты>"
      }
    }
  ]
}
```

### Маппинг в нашу схему

| Salebot Pro | Наше поле | Комментарий |
| --- | --- | --- |
| `platform_id` | `clients.tg_id` | Обязательно; без него клиент пропускается. |
| `name` / `full_name` | `first_name`, `last_name` | Делится по первому пробелу. |
| `tg_username` / `username` | `clients.username` | Ведущий `@` убирается. |
| `phone` | `clients.phone` | Строкой, как пришёл. |
| `email` | `clients.email` | Приводится к нижнему регистру. |
| `tarif` | `tariffs.code` | Числовой код Salebot Pro → код тарифа. |
| `datespis` | `subscriptions.current_period_end` | Дата окончания периода. |
| `tinkoff_rebill_id` / `rebill_id` | `subscriptions.rebill_id` | Для рекуррентных списаний. |
| `card_mask` / `tinkoff_card_mask` / `mask_card` | `subscriptions.card_mask` | Маска карты. |

Соответствие тарифов задаётся в коде миграции. Пример:

| Код Salebot Pro | Код проекта |
| --- | --- |
| 1 | `m1_legacy` |
| 2 | `m3_legacy` |
| 3 | `m6_legacy` |
| 4 | `m1` |
| 5 | `m3` |
| 6 | `m6` |

Если у вас другая нумерация, измените таблицу соответствия перед запуском.

### Даты и статусы

`datespis` может приходить в нескольких форматах: `ДД.ММ.ГГГГ`,
`ГГГГ-ММ-ДД`, `ДД.ММ.ГГ`, `ДД/ММ/ГГГГ` и с временем. Миграция пробует их
по очереди.

Статус определяется так:

- дата в будущем → `active`, `billing_enabled=true`;
- дата уже прошла, но попала в окно миграции (месяц переезда задан в коде) →
  `past_due`, `billing_enabled=false`;
- более старые даты → клиент пропускается.

Это позволяет не включать автоматические списания тем, у кого подписка уже
закончилась.

### Запуск миграции

```bash
# dry-run: только отчёт, без записи в базу
docker compose run --rm -v "$PWD/data:/app/data:ro" web \
  python -m app.migrate_salebot --ids data/example_ids.txt --dry-run

# применение
docker compose run --rm -v "$PWD/data:/app/data:ro" web \
  python -m app.migrate_salebot --ids data/example_ids.txt --apply
```

Образ не содержит каталог `data/`, поэтому он монтируется внутрь контейнера.
Можно запускать и из виртуального окружения на хосте:
`python -m app.migrate_salebot --ids data/example_ids.txt --dry-run`.

Файл `--ids` — по одному `client_id` Salebot Pro на строку; строки с `#`
игнорируются.

Отчёт показывает:

- сколько клиентов найдено;
- сколько перенесено;
- сколько пропущено;
- каких `client_id` нет в Salebot Pro;
- у кого нет `rebill_id`, телефона или email;
- ошибки `get_variables`.

Миграция идемпотентна: клиенты и подписки обновляются по `tg_id`, повторный
запуск не создаёт дублей. Сначала всегда делайте `--dry-run` и сверяйте
отчёт с ожиданиями.

## Путь 2. Бэкап схемы `.sbk`

В Salebot Pro: **Резервная копия → Скопировать схему**. Получится JSON-файл
`.sbk` с двумя ключевыми частями:

- `payload.schema.messages` — блоки сообщений и кнопок;
- `connections` — связи между блоками.

Это **образец логики**, а не файл для импорта в этот проект. Импорт `.sbk`
не поддерживается: формат внутренний и может меняться.

Как читать схему:

1. **Блоки.** Каждый блок — шаг сценария: приветствие, выбор тарифа, запрос
   имени, оплата, напоминание, выдача доступа. Выпишите порядок шагов.
2. **Связи.** `connections` показывают, из какого блока в какой ведёт переход
   и по какому условию. Это аналог наших состояний и callback-кнопок.
3. **Условия.** Ветвления «оплатил / не оплатил», «подписка активна /
   закончилась», «тариф такой-то» переносятся в проверки статуса подписки и
   тарифа.
4. **Калькулятор.** Если цена или срок считались формулой, перенесите
   значения в `tariffs.yaml`: код, название, цена в копейках, срок.
5. **Таймеры.** Отложенные сообщения и напоминания становятся задачами
   `reminder_3d`, `reminder_1d`, `charge` в планировщике.

Схема может содержать тексты и внутренние идентификаторы. Считайте её
приватным материалом: не публикуйте и не коммитьте.

## Путь 3. Текущая реализация как пример

Те же шаги в коде проекта:

| Шаг | Где смотреть |
| --- | --- |
| Старт и меню | `app/bot/handlers/start.py`, `app/bot/handlers/menu.py` |
| Регистрация: имя, email, телефон | `app/bot/handlers/registration.py` |
| Тарифы и цены | `content/example/tariffs.yaml`, `app/seed.py` |
| Создание платежа | `app/services/payments.py` |
| Приём уведомления банка | `app/web/routes_tbank.py`, `app/services/payments.py` |
| Напоминания и списания | `app/services/billing.py` |
| Выдача доступа | `app/services/post_payment.py`, `app/services/access.py` |
| Ответы админов | `app/bot/handlers/admin.py` |
| Отчёты | `app/reports.py` |

Порядок тот же, что в Salebot Pro: приветствие → выбор тарифа → контакты →
оплата → доступ → напоминания → продление или удаление доступа. Разница в
том, что состояние хранится в PostgreSQL, а отложенные шаги — в таблице
`jobs`, а не во внутренних таймерах конструктора.

## Переключение

### 1. Подготовка

- Сделайте бэкап базы Salebot Pro и сохраните точку восстановления.
- Выгрузите клиентов и переменные, сверьте количество и суммы.
- Зафиксируйте старые значения: URL уведомлений Salebot Pro, ключи терминала,
  вебхук Telegram.
- Получите согласие на перенос персональных данных.
- Подготовьте тестовый контур и проверьте его.

### 2. Заморозка Salebot Pro

- Удалите или отключите `TerminalKey` и `Password` в интеграции Salebot Pro с
  Т-Банком.
- Сохраните скриншот настроек без ключей.
- Не делайте тестовых списаний через Salebot Pro.

Пока ключи на месте, есть риск двойных списаний.

### 3. Перенос данных

```bash
docker compose run --rm -v "$PWD/data:/app/data:ro" web \
  python -m app.migrate_salebot --ids data/example_ids.txt --dry-run
docker compose run --rm -v "$PWD/data:/app/data:ro" web \
  python -m app.migrate_salebot --ids data/example_ids.txt --apply
```

Проверьте:

- число клиентов и подписок совпадает;
- нет дублей `tg_id`;
- у активных подписок `billing_enabled=true`;
- у просроченных `billing_enabled=false`;
- отсутствующие `rebill_id`, телефон и email перечислены и приняты.

### 4. Переключение уведомлений Т-Банка

В кабинете боевого терминала укажите:

```text
https://<ваш-домен>/tbank/notify
```

Сохраните скриншот. Старый URL Salebot Pro сохраните для отката.

### 5. Снятие вебхука Telegram

Новый бот работает через long polling, поэтому вебхук нужно снять:

```bash
curl -sS "https://api.telegram.org/bot<BOT_TOKEN>/deleteWebhook"
curl -sS "https://api.telegram.org/bot<BOT_TOKEN>/getWebhookInfo"
```

В `getWebhookInfo.result.url` должно быть пусто. Если старый вебхук оставить,
бот и Salebot Pro будут конфликтовать за обновления.

### 6. Тест 1 ₽

Последний шаг перед включением боевого биллинга — живой тест на 1 ₽ с
немедленным возвратом. Только с письменным согласием клиента.

- `Init` на 100 копеек;
- `Charge` по `RebillId`;
- `Cancel` на 100 копеек;
- проверка, что возврат виден в кабинете;
- проверка, что подписка клиента не продлилась.

Подробнее — [tbank.md](tbank.md).

### 7. Включение биллинга

- Убедитесь, что активные подписки имеют `billing_enabled=true`.
- Поставьте цикл напоминаний и списаний для активных подписок.
- Проверьте, что у просроченных нет задач `charge`.
- Запустите `bot`, `billing` и `heartbeat`.
- Проверьте `/healthz`, логи и первый платёж.

## Откат

Окно отката — до первых новых списаний. После списаний это уже инцидент:
нужна сверка и ручные возвраты.

1. Остановите `bot` и `billing`.
2. Верните старый `NotificationURL` в кабинете Т-Банка.
3. Верните ключи терминала в Salebot Pro.
4. Верните старый вебхук Telegram, если он был.
5. Проверьте, что Salebot Pro снова отвечает и получает обновления.
6. Не удаляйте новую базу и логи: они нужны для разбора.
7. Если списания уже прошли — сверьте `payments` и `payment_events`,
   верните деньги вручную с админом Т-Банка.
