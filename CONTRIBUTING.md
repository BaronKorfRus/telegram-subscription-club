# Участие в разработке

Спасибо за интерес к проекту. Ниже — как поднять окружение, прогнать проверки и
предложить изменение.

## Что нужно

- Python 3.13+
- Docker и Docker Compose
- PostgreSQL для тестов (можно в контейнере)
- `ruff` и `pytest` из dev-зависимостей

## Окружение

```bash
python -m venv .venv
. .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env
```

Для тестов нужна отдельная база. Поднимите её в Docker:

```bash
docker run --rm -d \
  --name club-test-db \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=club_test \
  -p 55432:5432 \
  postgres:16
```

и задайте строку подключения:

```bash
export TEST_DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:55432/club_test
```

Тесты сами применяют миграции к этой базе. Не используйте боевую базу: тесты
пишут данные.

## Проверки

```bash
pytest -q
ruff check .
```

Перед pull request обе команды должны проходить. Если менялась схема — добавьте
миграцию Alembic и проверьте её на чистой базе.

## Стиль

- Python 3.13, типизация там, где она помогает.
- Длина строки — 100 символов (`ruff`).
- Имена и структура — как в соседнем коде.
- Комментарии короткие и по делу, на русском.
- Без «умных» абстракций ради абстракции: проект небольшой.
- Один логический блок — один коммит.

## Тесты

- Новое поведение — сначала падающий тест, затем реализация.
- Тесты не должны зависеть от боевого контента, реальных ID и цен.
- Для платежей и Telegram используйте подмену HTTP-вызовов, а не реальные
  запросы.
- Тест на идемпотентность обязателен для всего, что меняет подписку или
  платёж.
- Не оставляйте тестовые данные в боевой базе.

## Контент

Код не должен содержать названий, доменов, ID и цен конкретного клуба.

- Тексты — `content/example/texts.yaml`.
- Тарифы — `content/example/tariffs.yaml`.
- Цены — в копейках, целым числом.
- Сроки — 30, 90 или 180 дней.
- Новые текстовые ключи добавляйте и в пример, и в загрузчик.

Если для изменения поведения достаточно правки YAML — это предпочтительный
путь.

## Приватные данные

В репозиторий не попадают:

- `.env`, токены, ключи, пароли;
- реальные ID каналов, чатов и клиентов;
- выгрузки Salebot, `.sbk`-схемы, списки клиентов;
- боевые тексты и цены;
- логи и бэкапы.

Перед коммитом проверьте diff на секреты и персональные данные. Если секрет
попал в историю — перевыпустите его, а не просто удалите файл.

## Документация

Публичные документы лежат в `docs-public/`. Это staging-каталог: при экспорте
`README.md`, `CONTRIBUTING.md` и `SECURITY.md` попадают в корень публичного
репозитория, остальные файлы — в `docs/`. Ссылки в текстах пишите сразу под
публичную раскладку.

- `README.md` — обзор, быстрый старт, ограничения.
- `architecture.md` — процессы, данные, идемпотентность.
- `self-hosting.md` — Docker, `.env`, Caddy, бэкап.
- `tbank.md` — терминал, подпись, чеки, уведомления.
- `salebot-migration.md` — три пути переезда.
- `security.md` — секреты, доступы, инциденты.
- `SECURITY-policy.md` — политика раскрытия уязвимостей; при экспорте
  становится `SECURITY.md` в корне.

`security.md` и `SECURITY.md` не могут лежать рядом в `docs-public/` на
macOS: файловая система не различает регистр. Поэтому политика хранится под
именем `SECURITY-policy.md`, а скрипт экспорта переименовывает её.

## Pull request

1. Опишите задачу и ожидаемое поведение.
2. Приложите вывод `pytest -q` и `ruff check .`.
3. Укажите, менялись ли схема, конфигурация и публичная документация.
4. Не смешивайте рефакторинг и поведенческие изменения в одном PR.
5. Будьте готовы к замечаниям: проверяйте их по коду, а не на слово.
